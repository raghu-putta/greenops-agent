Stage 1

Building the Intelligence Core

Stage 1 was about building the brain. Before we could alert anyone about anything, we needed an AI pipeline that actually understands cloud infrastructure — not just lists resources, but genuinely thinks about what's wasteful and why.

We used Google Agent Development Kit (ADK) with Gemini Flash as the underlying model. ADK lets you build multi-agent pipelines — chains of specialized AI agents that each handle one piece of the puzzle.

🛰️

Carbon Scout

Scans GCP Compute API for idle VMs, unattached persistent disks, and unused reserved IPs. The data collector — no judgment, just facts.

🧠

GreenOps Analyzer

Takes raw findings and calculates real dollar cost and CO₂ emissions. Applies carbon intensity factors (0.000233 kg CO₂/kWh) to compute environmental impact.

⚙️

Optimization Executor

Proposes specific actions — stop this VM, release that IP — but never auto-executes. Human approval gate is non-negotiable.

📋

Report Generator

Formats everything into human-readable summaries, HTML emails, and Slack Block Kit messages. Structures the story, not just the data.

These four agents run in a sequential pipeline — Scout → Analyzer → Executor → Reporter. Each one feeds its output to the next. The result is a complete, contextualized intelligence report with actual savings estimates and carbon numbers attached to real GCP resource names.

Stage 2

Automated Hourly Alerts

Stage 1 was reactive — you had to open the dashboard to see results. Stage 2 made it proactive. Now GreenOps comes to you. Every single hour, without you doing anything, it scans and sends a full report to your Gmail inbox and your Slack channel simultaneously.

Stage 2 — Part 1

Building scheduler.py

We created a dedicated scheduler.py module — a standalone notification engine with three main functions, each doing exactly one thing.

1

run_scan() — The GCP Scanner

Calls GCP Compute API directly to find: idle VMs (running but 0 CPU for hours), unattached persistent disks (provisioned but not mounted), unused reserved IPs (allocated but not pointing anywhere). Returns raw findings dict.

2

send_email(data) — Gmail SMTP

Sends a rich HTML email with findings table, cost savings estimate, and CO₂ impact. Uses Gmail App Password (not your real Gmail password) via smtplib.SMTP_SSL on port 465. Always sends — even when findings = 0.

3

send_slack(data) — Slack Block Kit

Posts a formatted Slack message using Block Kit — Slack's rich formatting system. Sections, dividers, bold text, stats. Uses Incoming Webhooks so no Slack bot token is needed. Just a URL.

4

run_scheduled_scan() — The Orchestrator

Calls all three in sequence: run_scan() → send_email() → send_slack(). Returns summary dict with email_sent: True and slack_sent: True for logging.

Stage 2 — Part 2

2

Generate the App Password

Stage 2 — Part 5

The /scheduled-scan Endpoint

We added one new POST endpoint to app.py — the automation trigger. Protected by a shared secret so only Cloud Scheduler can call it. Anyone without the right header gets a 401.

Python — app.py
@app.post("/scheduled-scan")
async def scheduled_scan(x_scheduler_secret: str = Header(default="")):
  expected = os.getenv("SCHEDULER_SECRET", "")
  if x_scheduler_secret != expected:
    raise HTTPException(status_code=401, detail="Invalid scheduler secret")

  from scheduler import run_scheduled_scan
  result = await asyncio.get_event_loop().run_in_executor(None, run_scheduled_scan)
  return JSONResponse(result)
Stage 2 — Part 6

Google Cloud Scheduler is like a cron job in the cloud — it fires HTTP requests on a schedule. We enabled the Cloud Scheduler API and created one job that fires every hour on the hour.

Stage 3

Debugging the Dashboard — From Broken to Live

After Stage 2 was confirmed working, we opened the dashboard browser UI to run a live test with all 4 agents streaming in real-time. That's when the problems started — four separate issues, one after another. Here's exactly what broke and how we fixed each one.

Stage 3 — Problem 1

API Key Invalid — Wrong Service Updated

Clicking Run Real GCP on the dashboard returned: 400 INVALID_ARGUMENT — API key not valid — API_KEY_INVALID. We updated the Gemini API key — but the error persisted after the deploy.

⚠️
Root Cause: Two separate Cloud Run services

The browser was pointing at greenops-dashboard-845589445410.us-central1.run.app but the gcloud run services update command was run against greenops-agent. Two different services, two different env vars. We updated the wrong one.

❌ What we ran (wrong)
gcloud run services update greenops-agent --update-env-vars "GOOGLE_API_KEY=..."
✅ What we needed (correct)
gcloud run services update greenops-dashboard --update-env-vars "GOOGLE_API_KEY=..."
Stage 3 — Problem 2

The Placeholder Key — Literal Text in Production

Even after targeting the correct service, the error persisted. We ran a diagnostic to check what was actually set as the GOOGLE_API_KEY on the service.

PowerShell — Diagnostic
gcloud run services describe greenops-dashboard \
  --region us-central1 \
  --format "value(spec.template.spec.containers[0].env)"

# Output showed:
GOOGLE_API_KEY = YOUR_KEY_HERE ← literal placeholder text!
🚨
Root Cause: Placeholder was never replaced

The command template showed GOOGLE_API_KEY=YOUR_KEY_HERE — and that literal string was deployed to the service without substituting the real key value. Classic copy-paste mistake.

Stage 3 — Problem 3

429 Resource Exhausted — Free Tier Quota Depleted

After deploying the real Gemini API key to the correct service, the dashboard threw a new error: 429 RESOURCE_EXHAUSTED — Quota exceeded for quota metric 'generate_content_request_count'

⚠️
Root Cause: Daily free quota exhausted

AI Studio's free tier key gives 1,500 Gemini API requests/day per project. That project's quota had been fully consumed during the earlier debugging runs — every failed attempt still counted as requests. Once the quota is gone for the day, the only options are: wait 24 hours, or generate a fresh key in a new GCP project (which has its own independent 1,500/day quota).

1

Option A — Wait for quota reset (rejected)

The free quota resets at midnight Pacific. Waiting ~24 hours wasn't acceptable when we were this close to a working system.

2

Option B — New key in a new GCP project (chosen)

Went to aistudio.google.com/app/apikey → Created a new project → Generated a fresh key. Each GCP project gets its own independent 1,500 req/day quota. Instant fresh start.

3

Updated both Cloud Run services

New key pushed to both services simultaneously: gcloud run services update greenops-dashboard --region us-central1 --update-env-vars "GOOGLE_API_KEY=NEW_KEY" gcloud run services update greenops-agent --region us-central1 --update-env-vars "GOOGLE_API_KEY=NEW_KEY"

Stage 3 — Problem 4

gcloud CLI Not Found Inside Cloud Run

After the API key was fixed and correctly deployed, the dashboard showed a new error: gcloud not found. Run: gcloud auth application-default login

This one was deeper. The original tools/gcp_tools.py was calling gcloud CLI as a subprocess — meaning it ran shell commands like subprocess.run(["gcloud", "compute", "instances", "list", ...]). That works perfectly on your Windows laptop where gcloud is installed. But inside a Cloud Run container? There is no gcloud binary. The container is a minimal Linux image.

❌ Old approach — gcloud subprocess (breaks in Cloud Run)
import subprocess
def _gcloud(*args):
  gcloud_cmd = shutil.which("gcloud") # None in Cloud Run!
  if gcloud_cmd is None:
    raise FileNotFoundError("gcloud not found")
  return subprocess.run([gcloud_cmd, *args], ...)
✅ New approach — Python SDK (works everywhere via ADC)
from google.cloud import compute_v1
from google.cloud import recommender_v1

def list_idle_vms(project_id: str) -> dict:
  client = compute_v1.InstancesClient() # ADC auto-auth
  for zone, data in client.aggregated_list(project=project_id):
    # returns real data — no CLI needed

In Cloud Run, Application Default Credentials (ADC) are automatically available via the service's attached service account. The Python SDK picks them up without any configuration. No gcloud, no JSON key file, no auth command — it just works.

1

Rewrote tools/gcp_tools.py

Replaced all subprocess.run(["gcloud", ...]) calls with google.cloud.compute_v1 and google.cloud.recommender_v1 SDK clients. Each function now uses the Python SDK with ADC authentication.

2

Updated requirements.txt

Added two new packages: google-cloud-compute and google-cloud-recommender. These are the official Google Cloud Python client libraries that handle auth, retries, and API calls cleanly.

3

Committed and Redeployed Both Services

Pushed to GitHub, then gcloud run deploy for both greenops-dashboard and greenops-agent. Revisions greenops-dashboard-00010-kkt and greenops-agent-00004-v2p deployed successfully.
